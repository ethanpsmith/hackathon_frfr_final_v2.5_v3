# Later bench-test prerequisites (not executed)

This is a review checklist for creating a separate controlled hardware procedure. The software here contains no hardware mode. No physical test, flashing, arming, motor spin or latch actuation was performed.

1. Record actual board/component revisions, pinouts, cables, voltage/current limits and firmware. Resolve the PM08 CAN interface, exact M10 compass, TFmini UART/I²C variant, RP4TD CRSF UART, SiK and companion UART allocations, and Remote ID transport. Keep a connector/power/output allocation table under review; do not substitute example wiring.
2. Independently measure assembled mass and CG with/without the 1.814 kg payload. Validate structural retention, landing/cradle clearances and dynamic rotor separation. Validate propulsion thrust/current/temperature and usable battery energy with appropriate protected equipment; the stock SITL model cannot supply these results.
3. Before any powered moving-output test, write a reviewed procedure covering restrained apparatus, props removed where applicable, protected power supplies, current limits, emergency isolation, observers and explicit abort criteria. Establish that sensor-only software cannot energize a release output. This document is not authorization to run such a test.
4. Validate PM08 readings and capacity accounting against instruments; simulate low/critical battery inputs safely. Determine actual 6S thresholds from sag, cell limits and required reserve. Never load the stock 3S SITL overlay onto Pixhawk.
5. Validate GNSS/compass orientation/calibration and interference, TFmini validity under expected lighting/surfaces/heights, RC receiver failure and operator recovery modes, and telemetry/companion loss behavior. Confirm no other heartbeat sender can mask companion loss.
6. Develop an independent hardware release interlock and verified contact/load/latch acquisition path. Test contradictory/stuck/disconnected signals, stale samples, actuator stalls and power loss with a supported inert test load. Positive support and separation must be demonstrated mechanically; a servo command or single contact switch is insufficient.
7. Calibrate the actual Camera Module 3 and mounting transform. Profile bounded capture/detection on the Pi Zero 2 W, including autofocus behavior, latency, CPU, memory and thermal load. Establish pad occupancy/approach validity separately from fiducial recognition.
8. Review MAVLink message ownership, signing/key provisioning and hardware gateway authorization. A compromised unrestricted UART peer can send commands beyond this Python API; the current API is not a hardened hardware command firewall. Require independent release and flight-controller protections before introducing a hardware transport.
9. Verify the actual Remote ID implementation and installation separately. The SITL build and simulated links provide no compliance evidence.
10. Only after the separate hardware procedure is reviewed should a human configure a dedicated bench-only hardware project. Progress through nonmoving sensor checks and controlled interlock tests before considering any HIL or flight procedure. Nothing in the simulation results approves autonomous flight.

Outstanding expansion work: actual Pi acquisition/drivers, independent hardware interlocks, validated 6S propulsion/dynamics/energy model, measured camera/range behavior, real occupancy sensing for approach gating, calibrated precision landing, a reviewed hardware command gateway, full ground-station/RC recovery integration, and a second clean-environment reproduction.
